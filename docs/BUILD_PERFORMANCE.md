# 建置效能與工具鏈

本文件保存首版工具鏈選擇的歷史量測與決策依據，不是目前每次建置的效能報告，也不作完整交付的驗收通過證明。現行開發入口見 [README.md](../README.md)，測試證據見 [TESTING.md](TESTING.md)，首版仍須完成的工具鏈與套件驗收見 [PLAN.md](PLAN.md)。以下數據保留原始環境、樣本與限制，不因文件整理更新為新量測。

## 工具鏈決策

- 固定 Bun 1.4.2 負責安裝與腳本入口，唯一鎖檔為 `frontend/bun.lock`；使用 frozen／ignore-scripts／hoisted，不跳過鎖檔驗證或法律收集。
- Node.js 明確執行 Vue 型別檢查、法律生成及發布工具。`scripts/frontend.mjs` 集中驗證版本與命令，不允許強制 Bun Runtime。
- Prettier／ESLint 由 Node 直接執行本地套件 CLI，不依賴 Windows npm `.cmd` 捷徑。
- Vitest 保留預設執行池與隔離；型別檢查及授權生成仍由各自入口執行。未採用 `vmThreads` 或共用前置生成的最佳化。

本文件記錄隔離對照實驗的固定條件與樣本，不代表完整打包耗時。**npm 對照組的主要等待是依賴重裝，不是 Vite 編譯**；局部差距不能換算為完整流程的加速比例，量測範圍也不能與其他來源的測試證據混用。

## 環境與方法

| 項目 | 量測條件                                                             |
| ---- | -------------------------------------------------------------------- |
| 系統 | Windows 10 企業版，10.0.19045，x86_64                                |

建置入口及型別工具各比較三輪，交替先後順序，取成功樣本中位數。安裝先以各自新快取執行一輪，再各跑三輪「共用工具快取、每輪全新目錄」，最後測同一安裝目錄。暖快取不代表作業系統冷啟動，單輪下載差異也不能歸因於工具本身。

分項檢查開始時已有 `frontend/dist/index.html`。Go 測試使用有效快取，未清除 Go／作業系統快取，也沒有以 `-count=1` 強制執行測試本體。

原始量測資料位於 `%LOCALAPPDATA%/Temp/opencode/build-timing-7fd6da84509f4488a4d790b4316d821c/`，含 metadata、逐項時間、日誌與量測腳本，不納入 Git。重測應使用獨立暫存目錄，記錄命令、版本、退出碼與每輪日誌；正式打包會寫產物與紀錄，不是無副作用的計時入口。

## 一、依賴安裝對照

只在各自暫存目錄放置對照 fixture，不刪除或替換專案 `node_modules`，均停用生命週期腳本：

```powershell
npm ci --ignore-scripts --no-audit --no-fund --cache $npmCache
bun install --frozen-lockfile --ignore-scripts --linker hoisted --cache-dir $bunCache
```

| 情境                         |    npm 秒 |    Bun 秒 | 樣本數 |
| ---------------------------- | --------: | --------: | -----: |
| 新建快取與安裝目錄，包含下載 |    161.35 |     80.27 |   各 1 |
| 暖快取、全新目錄，第 1 輪    |    109.54 |     12.53 |   各 1 |
| 暖快取、全新目錄，第 2 輪    |     87.63 |     12.95 |   各 1 |
| 暖快取、全新目錄，第 3 輪    |     75.23 |     10.58 |   各 1 |
| 暖快取、全新目錄，中位數     | **87.63** | **12.53** |   各 3 |
| 同一目錄再次執行             |     78.23 |      0.31 |   各 1 |

暖快取全新目錄的中位差約 85.7%。最後一列不是同等重裝：npm ci 清除並重裝，Bun 可檢查後保留現有安裝，不能把此差距當成乾淨安裝加速比例。

這組 Bun fixture 從 npm 鎖檔匯入並在暫存目錄產生 bun.lock；npm 鎖檔 SHA-256 未變。實際安裝的名稱／版本集合相同，共 251 組；含重複副本為 npm 252、Bun 253。此實驗不等同正式 Bun 鎖檔的完整依賴樹驗收。

另以全新暫存目錄與完整 npm 快取執行離線定位：

```powershell
npm ci --offline --timing --ignore-scripts --no-audit --no-fund --cache $npmCache
```

成功耗時 **77.57 秒**，`reify:unpack` 為 **73.65 秒**，約占牆鐘時間 95%；依賴樹計算約 0.12 秒。這只能定位至本機解包／安裝階段，未分解快取讀取、解壓、完整性校驗、寫檔及安全掃描，不可直接歸因於特定磁碟或防毒。

## 二、建置入口與 Runtime 對照

以下使用同一 npm 安裝樹，在 `frontend/` 執行，保留前置授權生成、型別檢查與 Vite；不是正式 Bun 乾淨樹的效能數據。

| 命令                  |  第 1 輪秒 |  第 2 輪秒 |  第 3 輪秒 | 中位數秒 |
| --------------------- | ---------: | ---------: | ---------: | -------: |
| `npm run build`       |       9.84 |       8.59 |       9.93 | **9.84** |
| `bun run build`       |       8.85 |       8.16 |       7.60 | **8.16** |
| Node 直接執行 vue-tsc |       4.81 |       4.92 |       4.73 | **4.81** |
| Bun 直接執行 vue-tsc  | 6.88，失敗 | 3.24，失敗 | 3.18，失敗 |   不適用 |

腳本入口差約 1.68 秒／17.1%。兩方均完成 339 模組，Vite 自報編譯時間為 npm 1.19 至 1.36 秒、Bun 1.16 至 1.17 秒。Bun 腳本的法律生成仍明確使用 Node，不能稱為全面替換 Runtime。

型別工具以相同入口對照：

```powershell
node ./node_modules/vue-tsc/bin/vue-tsc.js --noEmit
bun ./node_modules/vue-tsc/bin/vue-tsc.js --noEmit
```

Node 三次成功；Bun 三次均 exit 2，出現 22 筆 TS2307、無法辨識 `.vue` 模組。失敗耗時不能當成有效加速。此版本組合涉及 Volar 暫時覆寫 `fs.readFileSync` 注入 Vue 支援與 Bun CommonJS 原生讀取的相容性，參考 [issue 4754](https://github.com/oven-sh/bun/issues/4754) 與 [PR 35466](https://github.com/oven-sh/bun/pull/35466)；不據此推定其他版本的狀態。

正式入口由 Node 執行 vue-tsc，並以反向回歸確認 Vue 內字串賦 number 必須報 TS2322，而不是 TS2307 或悄悄通過；不得用萬用 `.vue` 宣告遮錯。

## 三、檢查流程時間分布

以下為 npm 對照組一次相同檢查命令序列，不含安裝。各前端階段已含授權前置工作，不能再加一次授權時間；工具測試為該 fixture 的 13 項，前端為 16 檔 74 項。專案完整測試範圍另見 [TESTING.md](TESTING.md)，不以對照 fixture 的數量代替。

| 階段                                      |        秒 |
| ----------------------------------------- | --------: |
| Go 測試，有效快取                         |      4.18 |
| Go vet                                    |      1.86 |
| gofmt                                     |      0.14 |
| 前端來源格式                              |      2.31 |
| 產生綁定格式                              |      1.16 |
| 前端 ESLint                               |      3.84 |
| `npm run typecheck`，含前置授權           |      7.69 |
| `npm run test`，含前置授權                | **19.60** |
| `npm run build`，含前置授權及再次型別檢查 |      9.60 |
| 打包工具格式                              |      0.59 |
| 打包工具 ESLint                           |      0.83 |
| Node 工具測試                             |      1.63 |
| **命令時間合計，以未四捨五入值計算**      | **53.42** |

全部命令成功，前端 16 檔 74 項通過。Vitest 自報 16.43 秒，jsdom 建立 16 次、占追蹤時間 44%；18.65 秒環境時間是多 worker 累計，不能直接自牆鐘時間扣除。

typecheck 與 build 各執行一次 vue-tsc，pretypecheck／pretest／prebuild 各生成授權。單獨授權三輪為 1.19／1.14／1.18 秒，中位數 **1.18 秒**，均收錄 50 元件；子程序追蹤的 go list 中位數約 **0.69 秒**，其他 Go／Git 約 0.31 秒。不能把整段授權工作視為腳本入口成本。

### Vitest 執行池對照

相同 Node、依賴、測試與預設隔離，交替各三輪；直接執行 Vitest，不含腳本入口或授權生成：

```powershell
node ./node_modules/vitest/vitest.mjs run
node ./node_modules/vitest/vitest.mjs run --pool=vmThreads
```

| 執行方式  | 第 1 輪秒 | 第 2 輪秒 | 第 3 輪秒 |  中位數秒 |
| --------- | --------: | --------: | --------: | --------: |
| 預設      |     18.49 |     15.34 |     17.91 | **17.91** |
| vmThreads |      7.90 |      7.63 |      7.38 |  **7.63** |

六次均通過 74 項，未減少測試、修改斷言、使用 isolate=false 或調整 worker 數。此條件少約 10.28 秒／57.4%，但不含前置成本，不能直接與前表 19.60 秒相減。正式設定仍使用預設池；採用其他執行池前須另行同意並驗證最低 Node、Linux 與長時間記憶體表現。

## 四、Go 編譯與相容性驗證

使用本機工具鏈與有效編譯快取，以 production／GUI／精簡旗標、development 版號輸出至新暫存檔：

```powershell
go build -tags production -trimpath -ldflags '-s -w -H windowsgui -X github.com/bestpika/go-fastly-ctrld/internal/version.Version=development' -o $temporaryExe ./cmd/go-fastly-ctrld
```

兩輪為 **2.90／2.80 秒**，不含乾淨快取編譯、Wails 圖示資源、四檔生成、壓縮、發布協調或啟動，不代表完整原生打包耗時。量測不讀寫真實帳號／金鑰庫，也不修改正式版本或發布紀錄。

混合工具鏈的乾淨 Bun 樹相容性證據為完整檢查通過、鎖檔不改寫，50 元件／58 份法律檔的原文與 SHA 一致。法律收集逐實體路徑走訪，只合併全部資料一致的副本；來源或法律差異停止建置。這組證據不是與 npm 對照組同條件的效能量測，測試數量與範圍見 [TESTING.md](TESTING.md)。

## 量測限制與維護原則

- 未取得現行完整 Bun／Node 打包的逐項時間，不能套用局部差距宣稱總加速比例。
- Linux 原生、最低工具鏈、不同磁碟／防毒設定及記憶體壓力未完成對照；不為量測關閉安全軟體或自行安裝環境。
- 首輪下載、快取與背景負載均會影響數字，三輪中位數不是跨機器效能保證。
- 減少重複型別／法律生成必須保留獨立入口的正確前置流程，不能跨來源誤用資產或刪除安全檢查；任何最佳化須另行授權。
